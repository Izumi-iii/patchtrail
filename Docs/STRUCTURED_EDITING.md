# 工具生成补丁：结构化编辑协议

## 目标和范围

DeepSeek 基线中，3 个任务出现共 7 次手写 Git diff 格式错误。本阶段将默认模型写入口改为 edit_files：模型提供精确替换，工具计算累计补丁，继续由原独立验证器验收。历史基线不修改，本阶段不调用真实模型或安装依赖。

## 输入契约

```json
{
  "expected_tree_hash": "当前工作树的 SHA-256",
  "edits": [
    {
      "path": "shop/refund.py",
      "expected_file_sha256": "read_file 返回的文件 SHA-256",
      "old_text": "    return original\n",
      "new_text": "    return original - discount\n"
    }
  ]
}
```

一次 1～30 个文件，每个文件一个替换，不能重复路径。可以用完整函数作为原文表达一个文件内的多处调整；原文必须非空且唯一匹配，包括重叠匹配也不得有歧义。输入上限 256 KiB，替换使用精确 UTF-8 / LF 文本，不剥离空白或偷偷归一化替换内容。

第一版只替换原始基准和当前候选中都存在的允许修改的 Python 文件，不创建、删除或重命名文件。new_text 可以为空以删除一个匹配片段，但不允许空 old_text 充当无锚点插入。可通过替换唯一上下文实现插入。

## 原子性与身份

1. 校验输入结构、工作树身份、路径和文件哈希。
2. 在内存中校验所有匹配、计算所有替换；缺失、重复匹配、过期内容和无效输入均不改变当前候选。
3. 计算“原始基准 → 编辑后的完整树”的 Git unified diff；由工具生成 hunk 行数、文件头、末尾无换行标记。
4. 在新的 proposal 目录保存结构化请求和生成补丁，并调用既有 apply_candidate 重放、检查实际文件清单与变更限制。
5. 只有整个批次成功、生成树等于预期树且原树未变化后，才发布新候选及补丁哈希。失败的 proposal 可以保留作证据，不是已发布候选。

提交候选后不允许继续编辑；反馈失败后由 Runner 明确解除冻结，才能修改。后续 edit_files 的原文和文件哈希针对当前候选，工具自动把之前的改动纳入累计补丁，模型无需重述之前的 diff。

路径越界、测试/配置文件修改和变更范围超限仍是策略拒绝；原文找不到、匹配歧义、过期哈希等输入问题可反馈给模型修正。系统检测到基准或当前快照被外部修改时终止，不把它当成普通输入错误。

## 兼容和验证

默认 TOOLS 和 Runner 不提供 propose_patch。直接使用 CodeTools 的兼容调用需显式 allow_legacy_patch=True，旧补丁解析测试继续保留；人工 verify.py 不变。正式 Runner 不允许通过未公开的工具名绕回旧入口。

候选 Git 重放使用独立配置，忽略宿主系统/全局 Git 配置并禁用自动换行转换；不修改宿主配置，也不改变读取输入仓库状态的规则。此前本机的 core.autocrlf 会把生成文件转换成 CRLF，新增加的精确树校验发现了这一问题。仓库自身属性若仍使输出字节变化，精确树核对会拒绝发布，不静默接受不同内容。CodeTools 由单个 Runner 顺序调用，不提供并发写接口。

验证重点：跨文件全部成功或全部拒绝、失败后旧候选与输入仓库不变、重复/重叠匹配拒绝、过期哈希、受保护路径、大小/变更限制、末尾无换行/空文件补丁、累计重试、冻结，以及工具生成补丁通过真实 Docker 独立验证。正式实现和验证结果在本文件后续记录。
